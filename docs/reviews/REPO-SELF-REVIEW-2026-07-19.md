## The three questions

### 1. Would a senior Google engineer immediately know this was "vibe-coded"?

**They would know within minutes that AI wrote most of it — because the repo says so — but they would not conclude it was vibe-coded, and the distinction is visible in the artifacts.** Every commit carries `Co-Authored-By: Claude`/PR trailers; `CLAUDE.md` is literally the AI reviewer's rubric. Nothing covers tracks, and nothing needs to. What separates this from LLM slop is discipline you can audit: 350 incremental commits whose messages explain *why* (`git log` reads as reasoned change, per the historian — fix-ratio and revert patterns normal), a PR gate with CI + browser smoke + adversarial AI review whose caught-bug trail is visible in issue threads, 114 unit-test files asserting real contracts (byte-identical cache prefixes, HMAC gating), and a consistent security idiom applied across ~40 routes.

Five classic tells **were** found and are real (appendix, "tells"): the twin-runner copy-paste (`chat-inline-runner.ts` vs `chat-run-worker.ts`, ~1,200 lines each, the same 13-step pipeline maintained by hand twice), a 2,530-line `ChatClient.tsx` god component, a TODO/dead-flag residue, I/O-tangled orchestration exactly where tests are thinnest, and validation done three ways across older routes. Nine tells were hunted and are **absent** — no secrets in code, no mock-everything vanity tests, no abandoned abstractions, no mixed paradigms, no naming drift, no overselling README. The found tells cluster in the two files where session-based development shipped fastest; they read as *known debt in a disciplined repo*, not as absence of engineering.

### 2. Or built by another strong engineer?

**Yes — that is the correct read, with the caveat that it's "a strong engineer moving very fast with AI leverage."** What earns it: the `AgentRuntime` seam (`packages/agent-runtime/src/types.ts:118-135`) that makes swapping Bedrock/AgentCore an env flip; a pure-logic `lib/` layer that keeps routing, edit-planning, and policy decisions testable and tested; per-user scoping applied systematically with encrypted-at-rest tokens (AES-256-GCM, fresh IV) and signed turn contexts; partial unique indexes used correctly for idempotency; DB-backed rate limiting; deliberate jsonb bounding via redact-and-truncate before persist; and a documented guard-order on the newest endpoint (`/api/apps/[id]/data/[bindingId]`) that the reviewers called "a model of scoped API design." The weaknesses are localized and known-shaped, not systemic.

### 3. Tear it down or evolve it?

**Evolve. Not close.** Kill criteria used: rebuild only if (a) the data model fights the product, (b) the security spine is unsound, or (c) duplication/incoherence is pervasive rather than localized. Measured: (a) data model scored 4/5 with correct integrity patterns; (b) security scored 4/5 with the spine *verified* — the failures found are two specific gaps (admin-write path, prompt-fold framing), not an unsound model; (c) the duplication is two files and one god component — painful, bounded, extractable. A rebuild would discard a working audited-execution ledger, a receipts system, and a test corpus for zero architectural gain. The hardening plan is at the end.

## System map (pre-verdict grounding)

**What this is, from the code:** a multi-tenant-by-user internal AI assistant: a Next.js App Router web app (chat threads, file uploads, versioned "workspace artifacts" that can be deployed as SSO-gated mini-apps, slash-activated "skills" with schedules and GitHub-webhook triggers) over a Bedrock ConverseStream agent loop with per-user OAuth tool connectors (GitHub/Notion/Google/Salesforce-read-only), a Postgres ledger of runs/run-events/audit rows underneath every execution, and an admin plane (run inspector with redacted traces, feedback inbox, model registry). Two execution lanes share one contract: an inline SSE streamer for interactive turns and a lease-based durable worker for background/scheduled runs, with an AWS AgentCore container as an alternate runtime target.

**Stack & size:** TypeScript throughout. ~62K LOC production (apps/web ~51K: app 15.2K / lib 27.1K / components 8.7K; packages: agent 2.6K, agent-runtime 0.6K, db 1.6K, evals 6.3K, agentcore-agent 0.4K) + ~29.4K LOC tests (vitest unit + Playwright e2e; ratio ≈ 0.47). pnpm workspace monorepo; 17 production deps in apps/web (lean: Next/React/Drizzle/next-auth + document-extraction libs). 350 commits.

**Entry points:** `apps/web` Next.js server (chat UI + ~40 API routes under `app/api/`); `apps/web/lib/chat-run-worker.ts` polling worker (separate ECS service); `apps/agentcore-agent` container (Bedrock AgentCore runtime lane); `packages/evals` CLI (`pnpm eval`, benchmark runners).

**Data flow:** browser → `POST /api/chat` (auth via NextAuth session → rate limit → attachment validation/extraction → thread+message persistence) → route selects lane → inline runner or queued run row claimed by worker → context pack assembly (history + summaries + Vault memory + artifact context, all receipt-tracked) → Bedrock ConverseStream with cached stable prefix + tool config from the discovery-bundle machinery → tool calls fan out to first-party MCP facades (per-user OAuth tokens decrypted per call, AES-256-GCM at rest) → every call redacted + audited (`audit_log`) + evented (`run_events`) → SSE stream to client / persisted rows on completion → artifacts minted from fenced blocks, versioned, optionally deployed at `/apps/{slug}` behind `canActorOpenApp` with per-viewer live-data bindings. Uploads: base64 → extraction (pdf-parse/mammoth/xlsx/jszip) → secret-scan → `workspace_artifacts` rows. Exit points: Bedrock, provider APIs (GitHub/Google/Notion/Salesforce), web search/fetch, SSE/JSON to the browser. No other egress.

**Production:** ECS services (web, worker, memory-capture) + RDS Postgres + AgentCore runtime, us-east-1; secrets in AWS Secrets Manager; CodeBuild webhook on main auto-builds and rolls all three ECS services (merge = live; docs-only commits skip deploy). Branch protection: CI (lint+typecheck+build), two Playwright smoke jobs, and an AI review verdict required; auto-merge on. Alpha: ~4 live users.

**Stage judgment frame:** graded as "strong engineer building an internal enterprise tool at alpha," where the stated spine — per-user scoping, honesty/receipts, auditability — is treated as a hard claim to verify, not marketing.

## Top 10 issues, ranked by consequence (impact × likelihood)

1. **The twin-runner fork has already produced policy drift** *(high, verified KKK)*. Two ~1,200-line hand-synced copies of the turn pipeline; the interactive lane never writes the denied-provider attestation audit row the worker writes, and only the inline lane re-validates model enablement at turn time (`chat-run-worker.ts:476-493` vs `chat-inline-runner.ts:336-339`; `162-169` vs `worker:631`). For a product whose pitch is audit rigor, an audit trail that depends on which lane a turn took is a credibility bug — and the fork is a *generator* of future instances of this class.
2. **Run-lifecycle correctness: stranded runs and unfenced leases** *(2 high findings, verified; panel-moderated)*. Inline runs stranded in `running` forever on process death (no reaper); lease reclaim/admin-resume can double-execute a turn and duplicate assistant messages — no `workerId` fencing on heartbeat or terminal writes; sequence allocation is non-atomic read-then-insert in three duplicate helpers with no unique constraint (`run-events.ts:82-96` + clones). Rare at 4 users; guaranteed embarrassment at 40.
3. **Cross-user scoping is structurally untestable today** *(high, verified KKK)*. The scope helper's test asserts predicate *presence*, and the fluent db-mocks discard WHERE clauses — so the spine claim rests on review vigilance, not tests. One compromised refactor could widen a query silently.
4. **`POST /api/chat` validates thread ownership with the read-side scope helper** *(high→moderated, verified)*. Admins can write into any user's thread — the helper's own doc says writes must use owner-scope. One-line class of fix; real trust-boundary defect.
5. **`xlsx@0.18.5` parses untrusted uploads with two known high CVEs and no npm fix** *(high, verified KKK)*. The upload path is authenticated-users-only today, which bounds it; an IT review will still flag it. Replace or sandbox the parser (exceljs, or parse in the worker with input caps).
6. **The 500ms pending-run poll drives an unbounded thread loader that fetches-and-discards full artifact content** *(high, verified; + unverified sibling on full-history refetch)*. First place the product falls over: one long background run + a few open tabs = RDS saturation from polling alone. Fix: poll a slim run-status endpoint; load artifacts lazily.
7. **Platform-wide background concurrency is 1** *(high, verified KKK)*. The worker claims one run at a time, globally. Fine at 4 users; the first simultaneous scheduled-skill pair breaks the "background work" promise. Bounded per-worker concurrency + a second worker task is the cheap unlock.
8. **No alerting action anywhere** *(high→moderated, verified)*. The sole CloudWatch alarm has no action; worker liveness unmonitored; 2am incidents are diagnosable (traces/receipts are genuinely good) but *undetectable*. One SNS topic + 3 alarms buys the whole rung.
9. **Deploy/rollback is mutable-`:latest`** *(high→moderated, verified)* and **drizzle meta snapshots are 12 migrations stale** *(same class)*. Rollback = ECR surgery; `db:generate` would emit wrong output (already community-known — the handwritten-SQL practice exists *because* of it, but the tripwire remains armed for a new engineer).
10. **Docs drift on the two authority documents** *(high→moderated ×2, verified)*. `TECHNICAL_OVERVIEW.md` misdescribes shipped state as of its own date; the "every capability is an MCP tool" rule is contradicted by shipped in-process web tools. Five research specs cite these as ground truth — drift compounds into planning error.

## Rebuild-vs-evolve: the hardening plan

**Evolve.** First three moves, sequenced by safety-per-effort:

1. **Extract `executeChatTurn`** — one shared pipeline core, two thin lane adapters (SSE/timing vs lease/heartbeat). Kills the drift-generator (Top-10 #1), makes orchestration unit-testable for the first time, halves every future turn-feature's change surface, and absorbs the helper-clone cleanup. *(~2-3 days, no behavior change, parity-pinned by the existing smoke.)*
2. **Run-lifecycle hardening** — `workerId` fencing on heartbeat/terminal writes, unique `(run_id, sequence)` index with retry, one sequence helper, and a stranded-run reaper (inline lane registers a lease too, or a startup sweep marks orphans failed). Closes Top-10 #2 wholesale. *(~1-2 days + one Rob-gated index migration.)*
3. **Ops floor** — digest-pinned image tags with one-command rollback, SNS-wired alarms (worker liveness, run-failure rate, DLQ-equivalent), and the slim run-status poll endpoint. Converts "diagnosable" into "detectable + reversible." *(~1-2 days.)*

Then, in order: scoping integration tests against a real Postgres (kills Top-10 #3's structural gap), the owner-scope fix on `POST /api/chat` (#4, trivial), xlsx replacement (#5), worker concurrency (#7), docs re-baseline (#10).

### Verified critical/high findings

**[Architecture & boundaries] Chat-turn pipeline forked into two ~1,200-line runners with confirmed behavioral drift** — high, votes `KKK` → SURVIVED  
Kind: defect. Evidence: apps/web/lib/chat-inline-runner.ts:190-716 and apps/web/lib/chat-run-worker.ts:285-793 implement the same 13-step turn pipeline; persist tails (persistInlineAssistantResult 718-1028 vs persistAssistantResult 795-1073) are near-byte-identical; identical local helpers duplicated (nextRunEventSequence, appendInline/WorkerRunEvent, numberFromEnv, uniqueStrings). Drift already shipped: turn-time model policy only inline (chat-inline-runner.ts:162-169 vs chat-run-worker.ts:631), providerHints for tool provider attribution only worker (createToolEventAccumulator([]) at inline:186 vs (mountedProviders) at worker:586), systemPrompt vs firstTurnPreamble used asymmetrically for the same content (inline:461 vs worker:634).  
Why: Every chat feature must be implemented twice and reviewed by hand-diffing two 1,200-line files; the drift instances found are exactly the audit/policy behaviors this product sells to enterprise IT. The in-file comments (#348, #359, #384, #416 appearing in both files) prove the 2x tax is being paid on every change, and the missing-audit case proves changes are already landing on one lane only.  
Fix: Extract a shared executeChatTurn core (context assembly, runTurn event consumption, persist tail) parameterized by a lane adapter: {emit(event), timing?, cancellation: signal|poll, onTerminal}. The inline runner becomes SSE-transport + timing; the worker becomes claim/lease/heartbeat + notification. Target: one persist function, one event loop, two <300-line shells.

**[Data model & persistence] 500ms pending-run poll drives an unbounded thread loader that fetches and discards full artifact content** — high, votes `KKK` → SURVIVED  
Kind: defect. Evidence: apps/web/app/chat/ChatClient.tsx:283 `const RUN_POLL_INTERVAL_MS = 500;` polling `/api/threads/${threadId}/messages`; apps/web/lib/thread-messages.ts:151-155 `db.select().from(workspaceArtifacts).where(inArray(...messageIds))` selects all columns including `content` (up to 500_000 chars per artifact, workspace-artifacts.ts:19), then workspace-artifacts.ts:242-264 serializes WITHOUT content; loader also has no LIMIT on messages (thread-messages.ts:76-92), runs (:93-121), or run_events (:128-149)  
Why: While any run is pending, every active user re-reads the entire thread history plus every artifact's full bytes from Postgres twice per second. Threads targeted by schedules accumulate runs/run_events/artifact versions monotonically, so this is the first thing that falls over at 100x data — DB bandwidth and RDS CPU, not row count, is the ceiling.  
Fix: Select explicit artifact columns (exclude content) in loadThreadMessagesWithRunActivity; bound runs/run_events to the visible window or add an updated-since cursor; raise the poll interval or reuse the existing SSE channel for pending-run updates.

**[API/interface design] Admin can write into any user's chat thread via POST /api/chat (read-scope helper on a write path)** — high, votes `KKK` → SURVIVED (severity moderated by panel: downgrade)  
Kind: defect. Evidence: apps/web/app/api/chat/route.ts:259-273 — thread lookup uses `userScope(sessionUser, chatThreads.userId)`, which for role=admin returns undefined (no filter) per apps/web/lib/auth/scope.ts:20-22, whose own doc (scope.ts:13-15) says "Read-side only — write/destructive routes keep their explicit ownership checks". The edit path proves the authors know this: chat/route.ts:305 has an explicit `thread.userId !== sessionUser.id` → 404 check that the plain-send path lacks.  
Why: The accident is fully wired in the product: ChatClient's sidebar fetches /api/threads (ChatClient.tsx:593), which for an admin returns ALL users' threads (threads/route.ts:16-17,61), so an admin clicking a teammate's thread and typing silently appends a user-role message into that user's thread, runs the agent under the admin's OAuth connections, and persists the assistant reply into the victim's thread (inline runner persists with threadId of the victim, userId of the admin). For a product whose stated spine is per-user data scoping under enterprise IT review, this is a cross-user write reachable by one misclick — and it contradicts the sibling routes' explicit doctrine (threads/[id]/route.ts:60-62,123-126: cross-user renames/deletes deliberately blocked).  
Fix: In POST /api/chat, replace the userScope lookup with an explicit `eq(chatThreads.userId, sessionUser.id)` for the send path (matching PATCH/DELETE), returning 404 for non-owned threads regardless of role; if admins genuinely need to converse in others' threads, make it an explicit admin endpoint with audit logging as the DELETE comment already prescribes.

**[Error handling & failure modes] Inline chat runs are stranded in 'running' forever on any uncaught error or process death** — high, votes `KKK` → SURVIVED (severity moderated by panel: downgrade,downgrade)  
Kind: defect. Evidence: apps/web/app/api/chat/route.ts:597 creates the run with status 'running' and no leaseExpiresAt; route.ts:793-800 catches streamInlineChatRun failures but only sends an SSE error — it never updates the run row. streamInlineChatRun (chat-inline-runner.ts:190-715) has try/finally but no catch: any throw in context assembly (lines 195-402) or in persistInlineAssistantResult's unguarded writes (lines 796-828, 927-966) escapes without marking the run failed. Worker reclaim can never rescue it: claimChatRun requires lt(runs.leaseExpiresAt, now) (chat-run-worker.ts:256), which is false for NULL.
